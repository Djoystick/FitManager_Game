# PROJECT CONTEXT: FitManager

Этот документ предназначен для быстрого и полного погружения новой AI-модели в контекст проекта, его архитектуру, текущий статус и правила взаимодействия. Прочитай этот файл перед началом работы, чтобы сохранить 연속ность (continuity) разработки.

## 1. ОПИСАНИЕ И ПРИНЦИПЫ

### Суть проекта (FitManager)
FitManager — это Telegram Mini App игра, в которой пользователь выступает в роли менеджера футбольной команды. Ключевая механика игры (Workout-to-Earn / W2E): развитие характеристик футболистов и восстановление их энергии напрямую зависят от реальных физических активностей пользователя (шаги, тренировки, синхронизированные через фитнес-приложения).
Игра включает в себя управление составом (Lineup/Pitch), тренировку игроков, трансферный рынок (Transfer Market) и участие в лигах.

### Технологический стек
- **Frontend:** Next.js (App Router), React, Tailwind CSS.
- **Backend & DB:** Supabase (PostgreSQL, Row Level Security, Edge Functions), Next.js Server Actions.
- **Language:** TypeScript (строгая типизация).
- **UI/Icons:** Lucide Icons, кастомные анимации (Tailwind `animate-in`, `framer-motion`), иконки исключительно с [icones.js.org](https://icones.js.org/).

### Главные архитектурные принципы
1. **Spec-Driven Development:** Сначала проектирование и план (Implementation Plan), потом написание кода. "Слепое" программирование (Vibe Coding) запрещено.
2. **Security & Review First:** Никакого YOLO Mode. Все Server Actions и API Route защищаются проверками авторизации (`user_id` / `telegram_id`), база данных закрыта политиками RLS (Row Level Security).
3. **Строгая типизация:** Минимизация использования `any`. Использование современных паттернов TypeScript, четкие интерфейсы для обмена данными между клиентом и сервером.
4. **Безопасная работа с БД:** Любые запросы к Supabase должны оборачиваться в `try/catch` с пробросом **реальных сообщений об ошибках** на клиент (а не абстрактных заглушек), чтобы обеспечивать понятный UI-фидбек (например, через `toast.error`).

## 2. ПОРЯДОК РАБОТЫ (Workflow)

### Взаимодействие и Отчетность
- Задачи выполняются поэтапно. После каждого логического шага генерируется markdown-отчет.
- **Правило чата:** В интерфейс чата запрещено выводить длинные куски кода, таблицы или объемные списки изменений. В чате должно быть только краткое уведомление (2-3 предложения) об успехе и **прямая ссылка** на сгенерированный отчет.

### Работа с отчетами (IDE Reports)
- Все подробные отчеты, архитектурные решения и инструкции по деплою сохраняются строго в папку `.ide_reports/`.
- Формат имени файла: `report_[тема_задачи]_[версия].md`.
- Содержимое отчета: список измененных файлов, логика принятых решений (Summary), написанные SQL-скрипты, инструкции по деплою (Commit & Push).

### Правила работы с базой данных (Supabase)
- **Изменение схемы:** Строго через файлы SQL-миграций в папке `supabase/migrations/` (в формате `XXXXX_name.sql`).
- **Каскадное удаление:** Обязательное использование `ON DELETE CASCADE` для всех зависимых таблиц (например, `players`, `matches`, `league_standings`, `infrastructure`, `league_matches`, `transfer_market`) при связях с базовыми таблицами вроде `users` или `teams`. Это критично для корректной работы функций вроде "Hard Reset".
- **Диагностика:** Если функция БД возвращает ошибку, следует выводить/логировать реальную причину (constraint violation, RLS block и т.д.), а не скрывать её за фразой "Internal Server Error". Использовать SQL-поиск (grep) для выявления связей.

## 4. ПАМЯТКА ДЛЯ МОДЕЛИ (System Prompt / Rules of Engagement)

При работе в новом чате строго соблюдай следующие правила поведения:
1. **Будь краток в чате:** Отвечай по существу, без "воды". Твой финальный ответ должен состоять только из 2-3 предложений и ссылки на отчет в `.ide_reports/`.
2. **Пиши подробные отчеты в `.md`:** Все размышления, диффы кода и инструкции по запуску помещай в файл отчета.
3. **Требуй логи перед выводами:** Если возникает баг, не пытайся угадывать. Добавляй/проверяй вывод логов, изучай структуру базы данных через чтение SQL-миграций или запрашивай логи сервера.
4. **Сохраняй чистоту кода (Context Hygiene):** Читай (через `view_file`) только те файлы, которые нужны для задачи. Используй точные инструменты вроде `grep_search`. Не перезаписывай файлы вслепую — уважай существующие докстринги и комментарии, не относящиеся к твоей задаче.
5. **Следуй стандартам (Microsoft AI Engineering):** Заглядывай в директорию `.ai-tools/AI-Engineering-Coach` (если она есть) при сомнениях. Сначала план (Plan Mode), затем реализация.
